# 1. 프로젝트 목표와 범위

## 배경

인기 굿즈나 콘서트 티켓이 열릴 때마다 "서버가 터졌다", "페이지가 멈췄다"는 말이 나온다. 직접 구매했을 때도 구매 버튼을 누른 뒤 화면이 멈춰 있다가 갑자기 결제 성공으로 넘어간 적이 있다. 짧은 순간에 많은 사람이 동시에 구매를 시도하는 이 장면에서 질문이 이어졌다.

- 한꺼번에 몰려드는 구매자를 멈추지 않고 받아들이려면 어떻게 해야 할까?
- 동시에 들어온 구매를 어떻게 처리해야 수량과 결과가 어긋나지 않을까?
- 외부 결제가 실패하거나 응답이 없을 때, 구매자의 결과는 어떻게 맞춰 줘야 할까?

그리고 그 결과가 구매자에게 공정하다고 느껴지는가. 참고한 판매와 구매 흐름은 [도메인 스토리](02-domain-story.md)에 있다.

이전 실험([limited-goods-experiments](https://github.com/tldnr1/limited-goods-experiments))에서 재고 처리 방식을 비교한 적이 있다. 여기서는 그 결과를 근거로 쓰지 않고, 이 저장소에서 다시 검증한 결과만 쓴다.

## 검증 목표

| | 질문 | 목표 | 검증 방법 | 범위와 한계 |
|---|---|---|---|---|
| A | 수량과 결과가 어긋나지 않게 | 동시 요청과 재요청에도 수량과 구매가 맞게 유지된다 | 테스트: 동시 요청에서 초과 판매와 중복 구매 0건, 테스트마다 수량 불변식 확인 | 서버 1대, DB 1개 기준 |
| B | 결제 실패와 무응답 시 결과 맞추기 | 상품을 받지 못한 구매에 결제가 남아 있지 않다 | 테스트: 결제 거절, 무응답, 늦은 승인을 주입하고 재처리 후의 최종 상태 확인 | 결제사는 대역으로 대신한다 |
| C | 몰려드는 구매자 받아들이기 | 부하 상황에서 지표로 병목을 찾고 개선한다 | 수치: 부하 테스트와 서버 지표를 함께 수집하고, 같은 조건에서 전후를 비교한다. 구매자가 결과를 기다리는 시간을 포함하며, 결과로 처리 규모를 추정한다 | 로컬 환경 측정. 병목을 찾지 못하면 측정 결과와 한계를 남긴다 |

세 목표를 모두 깊게 다룬다. 규칙과 시나리오는 [정책과 시나리오](03-policies-scenarios.md)에, 선택 이유는 ADR로, 측정은 실험 기록으로 남긴다([문서 관리](CONTRIBUTING.md#문서-관리)).

## 범위

| 영역 | 깊이 | 이유 |
|---|---|---|
| **수량 확보**: 구매 시도를 순서대로 받아 수량을 잡고, 1인 한도와 중복 시도를 처리하고, 풀린 수량을 돌려놓아 다시 판다 | 깊게 | 목표 A. 동시에 들어온 구매가 실제로 부딪히는 곳 |
| **결제 확정**: 결제 시간 규칙을 지키고, 결제사 오류 시 확인과 취소를 끝까지 다시 처리한다 | 깊게 | 목표 B |
| 결제사 | 얕게 | 실제 연동 없이 대역으로 둔다. 거절, 무응답, 늦은 승인, 취소 실패를 일부러 만들 수 있어야 한다 |
| 행사와 품목 정보 | 얕게 | 미리 등록된 정보로 시작한다. 판매 시작 시각, 수량, 1인 한도만 읽는다 |
| 구매자 식별 | 얕게 | 가입이나 로그인 없이 누구인지만 구분한다 |
| 구매 상태 조회 | 얕게 | 결제 결과를 바로 모를 때 구매자가 결과를 확인하는 창구 |
| 여러 품목, 입장 제어 | 고도화 | 아래 참고 |

C는 영역이 아니라 수량 확보와 결제 확정이 몰림을 견디는지에 대한 목표라 표에 없다.

## 고도화 주제

지금 만들지 않는다. 다만 더할 때 이미 만든 구조를 다시 만들지 않도록 설계에 반영한다. 흐름은 [도메인 스토리](02-domain-story.md#고도화-이야기)에 있다.

- **여러 품목**: 지금은 행사에 품목 하나를 판다. 품목이 여럿이 되어도 구매, 품목별 수량, 품목별 1인 한도의 저장 구조를 바꾸지 않아도 되게 설계한다. 확장한 뒤에는 C와 같은 조건에서 품목 수만 바꿔 측정한다.
- **입장 제어**: 수량 확보는 구매자가 어떻게 들어왔는지 모른다. 입장 제어는 구매 요청 앞에 더하고, 입장한 뒤의 순서 규칙은 그대로 쓴다.

## 범위 밖

- 실서비스 운영: 클라우드 배포, 실사용자 트래픽, 운영 모니터링
- 프론트엔드 화면
- 구매자가 요청하는 환불, 봇과 부정 구매 방지, 회원 가입, 행사와 품목 등록 과정

## 제약

- JVM 언어와 Spring 기반으로 구현한다. 구체적인 선택은 설계에서 한다.
- 캐시와 "접수 후 결과 안내" 방식은 C의 개선 수단 후보다. 쓸지는 측정 결과를 보고 정한다.
