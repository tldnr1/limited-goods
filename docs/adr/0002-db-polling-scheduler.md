# ADR-0002. 재처리는 앱 안 스케줄러가 DB를 주기적으로 확인해 실행한다

- 상태: 채택

## 맥락

결제 시작 기한 만료(P5, P6), 결제 결과 재확인(P7, P8), 결제 취소와 수량 반환의 재시도(R1)는 요청 없이도 실행되어야 하고, 앱이 다시 시작해도 사라지면 안 된다. 실행 시점이 결과에 주는 영향은 작업마다 다르다.

- 결제 시작 기한 만료: 기한 뒤의 결제 요청은 만료 처리 전이라도 무효라(T1) 그 구매의 결과는 바뀌지 않는다. 다만 수량이 늦게 돌아오는 동안 다른 구매자는 품절을 받는다.
- 결제 결과 재확인: 앱이 승인을 알게 된 시각이 확인 기한 뒤면 결제사가 기한 전에 승인했어도 구매는 실패하고 결제는 취소된다(P8, B9a). 재확인 시점이 최종 결과를 바꾼다.

## 결정

앱 안의 스케줄러가 DB에서 기한이 지났거나 다시 확인할 때가 된 행을 주기적으로 찾아 처리한다. 여러 실행이 같은 행을 집지 않도록 `FOR UPDATE SKIP LOCKED`로 가져온다.

## 고르지 않은 대안

- 메모리 타이머: 기한에 맞춰 바로 실행하지만, 재시작하면 사라져 DB 확인을 따로 둬야 한다. 구현이 둘이 된다.
- 메시지 큐의 지연 메시지: 기본 구성에 큐를 더한다. 큐는 C의 개선 후보라 기준선에 넣지 않는다.

## 결과

- 추가 인프라 없이 재시작에도 재처리가 이어진다.
- 확인 주기만큼 수량이 늦게 돌아온다. 주기는 C에서 바꿔 볼 변수다.
- 확인 기한 안에 결제 결과를 조회할 기회도 주기에 묶인다. 기한 전 마지막 조회를 어떻게 보장할지는 확인 기한, 재시도 간격과 함께 정한다.
- 확인 쿼리가 DB 부하에 더해진다. 부하 측정에서 따로 본다.
