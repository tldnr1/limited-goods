# 개발 규칙

하나의 문제를 변경하고 검증하는 단위로 작업합니다. 범위와 정책은 [목표와 범위](01-project-goals.md), [정책과 시나리오](03-policies-scenarios.md), 설계 결과를 기준으로 합니다.

## 브랜치와 변경 단위

- `main`은 검토를 마친 기준입니다. 실행 골격이 생긴 이후에는 빌드와 관련 테스트가 통과한 상태를 유지합니다.
- 최신 `main`에서 `feat/purchase`, `fix/payment-recovery`, `docs/project-goal`처럼 목적을 드러내는 짧은 작업 브랜치를 만듭니다. 장기 `develop` 브랜치는 두지 않습니다.
- 하나의 PR에는 하나의 목적을 담습니다. 관련 코드, 테스트, 정책 문서는 함께 검토하고, 무관한 정리는 분리해 검토와 되돌리기 범위를 명확히 합니다.
- 기본 병합 방식은 Squash merge이며 PR 제목을 최종 커밋 제목으로 사용합니다. 병합 후 작업 브랜치를 삭제합니다.
- 공유된 `main` 이력은 재작성하지 않습니다. 푸시, GitHub PR 생성, 병합은 저장소 소유자가 수행합니다.

## 커밋

형식은 `<type>(선택적 범위): 변경 내용`입니다. 제목은 변경 결과가 드러나도록 한국어로 작성하고, 제목만으로 설명하기 어려운 이유가 있을 때 본문을 추가합니다.

| 유형 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 잘못된 동작 수정 |
| `docs` | 문서 변경 |
| `refactor` | 동작을 유지하는 구조 개선 |
| `test` | 테스트와 검증 시나리오 변경 |
| `perf` | 성능 개선을 위한 변경 |
| `chore` | 설정, 의존성, 자료 정리 |
| `ci` | 자동 검사와 빌드 흐름 변경 |

```text
feat(order): 단일 상품 재고 점유 구현
fix(payment): 응답 유실 후 중복 결제 방지
docs: 첫 버전 구매 범위와 검증 방향 정리
```

파일 수보다 함께 되돌릴 수 있는 변경의 의미를 기준으로 커밋을 나눕니다. `수정`, `작업 완료` 같은 제목은 피합니다. 커밋 전 diff와 포함할 파일을 확인하고, 파일 경로를 명시해 스테이징합니다.

## PR과 검증

PR 제목은 커밋 형식을 따릅니다. 본문은 **배경, 변경, 확인**으로 구성하고, 필요한 경우 재현 조건과 남은 한계를 덧붙입니다. 변경 파일 목록이나 작업 일지를 반복할 필요는 없습니다.

- 구현 변경은 관련 동작을 검증한 명령과 결과를 남깁니다.
- 문서 변경은 정책 충돌, 범위, 링크를 확인합니다.
- 성능 개선은 비교 조건과 측정 결과를 함께 제시합니다.
- 미실행, 실패, 통과한 검사를 구분합니다.

변경 범위가 맞고, 중요한 리뷰 지적이 해결됐으며, 필요한 검증이 끝났을 때 병합합니다. 서비스 정책 변경이 필요한 기능은 구현에 앞서 정책을 논의합니다.

## 문서 관리

문서는 현재 기준, 변경 과정, 이력으로 나누고, 같은 내용은 한 곳에만 둡니다.

| 구분 | 문서 | 코드와 다를 때, 바뀔 때 |
|---|---|---|
| 현재 기준: 요구사항 | [정책과 시나리오](03-policies-scenarios.md) | 코드가 틀린 것으로 봅니다. 규칙은 정책을 바꾸기로 합의했을 때만 고칩니다. 시나리오에는 테스트 이름을 연결합니다 |
| 현재 기준: 설계 | [설계](04-design.md) | 의도한 변경이면 그 PR 안에서 코드와 함께 고칩니다 |
| 현재 기준: 배경 | README, [목표와 범위](01-project-goals.md), [도메인 스토리](02-domain-story.md) | 목표나 범위가 바뀔 때만 고칩니다 |
| 변경 과정 | 작업 지시, 범위 밖 발견 (저장소 밖) | 병합하면 지우고, 남길 내용은 PR 본문이나 기준 문서로 옮깁니다 |
| 이력: 결정 | `docs/adr/` | 내용은 고치지 않습니다. 결정이 바뀌면 새 ADR을 쓰고, 이전 ADR의 상태를 대체됨으로 바꿔 새 ADR을 링크합니다 |
| 이력: 측정 | `docs/experiments/` | 고치지 않습니다. 다시 측정하면 새 기록을 남깁니다 |
| 이력: 변경 | PR 본문, squash 커밋 | 병합 후에는 고치지 않습니다 |

설계 문서는 인프라와 애플리케이션 구성, 레이어 규칙, 모듈과 인터페이스, 상태 전이, ERD, API를 담습니다. 모듈 내부 구현은 적지 않습니다.

ADR은 구조, 품질 특성(정합성, 성능), 외부 의존, 인터페이스 중 하나에 영향을 주고 되돌리는 비용이 큰 결정만 씁니다. 결정할 때 상태(제안, 채택, 대체됨)와 함께 맥락, 결정, 고르지 않은 대안, 결과를 짧게 적습니다. 측정으로 정한 결정은 실험 기록을 링크합니다.

실험 기록은 측정 전에 고정 조건, 지표, 채택 기준, 바꿔 볼 범위를 먼저 적습니다. 결과는 시도마다 한 줄씩 표로 쌓고 채택 여부를 표시한 뒤, 원인 분석과 재현 자료를 덧붙입니다. 기대와 다른 결과도 결론으로 남깁니다.

더 이상 맞지 않는 문서는 보관 폴더로 옮기지 않고 고치거나 지웁니다. 이전 내용은 git 이력으로 확인합니다. 작업 진행 상황, 조사 원문, 세션 로그는 저장소에 남기지 않고, 조사의 결론만 출처와 함께 PR이나 ADR로 옮깁니다.

문장은 결정과 근거 위주로 짧게 쓰고 꾸밈말과 반복을 피합니다. 계획과 구현 및 측정 결과를 구분합니다. README의 문제와 결과는 구현 후에 쓰고, 자세한 규칙은 기준 문서로 링크합니다.
