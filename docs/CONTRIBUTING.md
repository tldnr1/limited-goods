# 개발 규칙

하나의 문제를 변경하고 검증하는 단위로 작업합니다. 범위와 정책은 [작업 지침](../AGENTS.md)의 진행 단계에서 합의한 문서를 기준으로 합니다.

## 브랜치와 변경 단위

- `main`은 검토를 마친 기준입니다. 실행 골격이 생긴 이후에는 빌드와 관련 테스트가 통과한 상태를 유지합니다.
- 최신 `main`에서 `feat/purchase`, `fix/payment-recovery`, `docs/project-goal`처럼 목적을 드러내는 짧은 작업 브랜치를 만듭니다. 장기 `develop` 브랜치는 두지 않습니다.
- 하나의 PR에는 하나의 목적을 담습니다. 관련 코드, 테스트, 정책 문서는 함께 검토하고, 무관한 정리는 분리해 검토와 되돌리기 범위를 명확히 합니다.
- 기본 병합 방식은 Squash merge이며 PR 제목을 최종 커밋 제목으로 사용합니다. 병합 후 작업 브랜치를 삭제합니다.
- 공유된 `main` 이력은 재작성하지 않습니다. 푸시, GitHub PR 생성, 병합은 저장소 소유자가 수행합니다.

## 커밋

형식은 `<type>(선택적 범위): 변경 내용`입니다. 제목은 변경 결과가 드러나도록 한국어로 작성하고, 제목만으로 설명하기 어려운 이유가 있을 때 본문을 추가합니다.

| 유형 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 잘못된 동작 수정 |
| `docs` | 문서 변경 |
| `refactor` | 동작을 유지하는 구조 개선 |
| `test` | 테스트와 검증 시나리오 변경 |
| `perf` | 성능 개선을 위한 변경 |
| `chore` | 설정, 의존성, 자료 정리 |
| `ci` | 자동 검사와 빌드 흐름 변경 |

```text
feat(order): 단일 상품 재고 점유 구현
fix(payment): 응답 유실 후 중복 결제 방지
docs: 첫 버전 구매 범위와 검증 방향 정리
```

파일 수보다 함께 되돌릴 수 있는 변경의 의미를 기준으로 커밋을 나눕니다. `수정`, `작업 완료` 같은 제목은 피합니다. 커밋 전 diff와 포함할 파일을 확인하고, 파일 경로를 명시해 스테이징합니다.

## PR과 검증

PR 제목은 커밋 형식을 따릅니다. 본문은 **배경, 변경, 확인**으로 구성하고, 필요한 경우 재현 조건과 남은 한계를 덧붙입니다. 변경 파일 목록이나 작업 일지를 반복할 필요는 없습니다.

- 구현 변경은 관련 동작을 검증한 명령과 결과를 남깁니다.
- 문서 변경은 정책 충돌, 범위, 링크를 확인합니다.
- 성능 개선은 비교 조건과 측정 결과를 함께 제시합니다.
- 미실행, 실패, 통과한 검사를 구분합니다.

변경 범위가 맞고, 중요한 리뷰 지적이 해결됐으며, 필요한 검증이 끝났을 때 병합합니다. 서비스 정책 변경이 필요한 기능은 구현에 앞서 정책을 논의합니다.

## 문서 관리

README는 소개와 현재 상태, 상세 문서로 가는 링크를 제공합니다. 단계별로 합의한 내용은 `docs/`의 기준 문서 하나를 갱신하며, 상세 설계, API, ERD는 결정할 내용이 생길 때 추가합니다. 같은 명세를 여러 곳에 복제하지 않습니다.

선택 이유와 남은 한계를 함께 기록하고, 계획과 구현 및 측정 결과를 구분합니다. 실험 기록은 실제 실험이 생기면 문제별로 남기며, 조건, 관찰, 원인, 변경 전후와 재현 자료를 포함합니다. 일정과 작업 목록은 필요한 이슈와 PR에서 관리합니다.
